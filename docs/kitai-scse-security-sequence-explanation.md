# Взаимодействие KitAI Core, SCSE MCP и scse-mid

Этот документ поясняет детальную диаграмму
[`kitai-scse-dynamic-tools.puml`](kitai-scse-dynamic-tools.puml).

Диаграмма показывает техническое взаимодействие систем при получении списка
MCP-инструментов и вызове выбранного инструмента. Внутреннее устройство SCSE MCP
и библиотеки `mcp-security-starter` намеренно не раскрывается: оба компонента
рассматриваются как чёрные ящики с определёнными входами и выходами.

## Назначение решения

Пользователь работает не с MCP-сервером напрямую, а через ИИ-агента. Агент
обращается к KitAI Core, а KitAI Core выступает MCP-клиентом и прокси для SCSE
MCP.

SCSE MCP должен решить две задачи:

1. Вернуть агенту только те динамические tools, которые доступны конкретному
   пользователю, конкретному агенту и конкретной поверхности.
2. При вызове tool повторно проверить доступ и выполнить соответствующий шаблон
   через backend-сервис `scse-mid`.

Таким образом, решение о доступе принимается с учётом сочетания:

```text
пользователь × агент × поверхность × tool
```

## Участники взаимодействия

### Agent Runtime

Среда выполнения ИИ-агента. Агент получает запрос пользователя, запрашивает
доступные инструменты, выбирает подходящий tool и инициирует его вызов.

### KitAI Core

Выступает MCP-клиентом и прокси. KitAI Core передаёт в SCSE MCP:

- MCP JSON-RPC запрос;
- JWT системы управления доступом AI HUB — опционально;
- JWT СУДИР для работы с SCSE — обязательно;
- JWT поверхности — точный контракт пока не определён;
- `AgentInfo` — точный формат и способ подтверждения пока не определены.

KitAI Core не принимает решение о доступности SCSE tools. Это решение принимает
SCSE MCP.

### SCSE MCP Server

Точка входа для MCP-запросов из KitAI Core. На диаграмме сервер показан как
чёрный ящик.

Его ответственность:

- принять `tools/list` или `tools/call`;
- получить проверенный контекст вызывающей стороны;
- проверить доступ по сочетанию пользователя, агента, поверхности и tool;
- сформировать персональный список динамических tools;
- сопоставить вызванный tool с шаблоном SCSE;
- обратиться к `scse-mid` для выполнения разрешённого шаблона;
- вернуть результат в формате MCP.

### mcp-security-starter

Общая библиотека для работы с security-контекстом MCP-запроса. Её внутреннее
устройство на текущем этапе не проектируется.

На уровне внешнего контракта библиотека должна:

- принять набор токенов и `AgentInfo` в виде `SecurityEnvelope`;
- проверить предусмотренные контрактом токены;
- вернуть нормализованный `McpCallerContext`;
- предоставить SCSE MCP корректный заголовок `Authorization` для вызова
  `scse-mid`;
- не раскрывать значения JWT прикладным tools и языковой модели.

В перспективе библиотека может использоваться повторно, однако другие
MCP-серверы не входят в границы данной диаграммы.

### scse-mid

Backend-сервис SCSE, предоставляющий REST API для работы с шаблонами и
выполнения запросов.

SCSE MCP обращается к `scse-mid` с СУДИР JWT в стандартном заголовке:

```http
Authorization: Bearer <СУДИР JWT>
```

`scse-mid` повторно проверяет JWT и права на защищённом endpoint. Проверка на
стороне MCP не отменяет проверку на backend.

### Системы управления доступом

На диаграмме показаны три источника доверия:

- СУД AI HUB — для AI HUB JWT;
- СУДИР — для пользовательского токена SCSE;
- СУД поверхности — контракт пока не определён.

Под `issuer / JWKS / claims contract` понимается доверенная конфигурация,
необходимая библиотеке для проверки токена: ожидаемый издатель, открытые ключи,
audience и обязательные claims. Получение JWKS может происходить при запуске или
периодическом обновлении кеша, а не обязательно при каждом MCP-запросе.

## Входной security-контекст

На диаграмме используется логическое название `SecurityEnvelope`. Это ещё не
конкретный Java-класс и не окончательный HTTP-контракт, а обозначение входного
набора данных безопасности.

Предполагаемый состав:

| Данные | Обязательность | Назначение |
|---|---:|---|
| AI HUB JWT | Опционально | Идентификация KitAI Core или вызывающей системы AI HUB |
| СУДИР JWT | Обязательно | Идентификация пользователя SCSE и авторизация в `scse-mid` |
| Surface JWT | Не определено | Идентификация поверхности, из которой инициирован запрос |
| AgentInfo | Не определено | Идентификация агента, инициировавшего вызов tool |

Точные имена HTTP-заголовков пока не определены. Все токены должны передаваться
на транспортном HTTP-уровне, а не как аргументы MCP-tool. Иначе токены могут
попасть в JSON Schema инструмента, контекст языковой модели или пользовательские
логи.

## McpCallerContext

Результатом успешной обработки `SecurityEnvelope` является
`McpCallerContext` — нормализованный и проверенный контекст вызывающей стороны.

Логически он может содержать:

```text
userId и роли пользователя
agentId
surfaceId
coreClientId, если передан AI HUB JWT
```

SCSE MCP должен работать с этим контекстом, а не самостоятельно разбирать JWT.
Точный состав модели будет зафиксирован после согласования всех входных
контрактов.

Особое внимание требуется `AgentInfo`. Обычный идентификатор, переданный
клиентом как строка, можно подменить. Поэтому `agentId` должен быть связан с
подписанным токеном либо передаваться по аутентифицированному доверенному каналу
KitAI Core.

## Получение персонального списка tools

### 1. Запрос от агента

Agent Runtime инициирует MCP-операцию через KitAI Core и передаёт доступную
информацию об агенте.

### 2. Вызов `tools/list`

KitAI Core отправляет в SCSE MCP запрос `tools/list` вместе с тремя JWT и
`AgentInfo`. Опциональность и формат отдельных элементов должны быть закреплены
в интеграционном контракте.

### 3. Аутентификация контекста

SCSE MCP передаёт полученный `SecurityEnvelope` в `mcp-security-starter`.
Библиотека проверяет входные данные и при успехе возвращает
`McpCallerContext`.

Если обязательный токен отсутствует, истёк, имеет неправильную подпись,
неподходящий issuer или audience, запрос считается неаутентифицированным. В этом
случае KitAI Core получает `401 Unauthorized`.

### 4. Фильтрация tools

Для аутентифицированного контекста SCSE MCP определяет, какие tools разрешены по
совокупности:

```text
user × agent × surface × tool
```

KitAI Core получает только разрешённые tools. Недоступные инструменты не должны
попадать в ответ `tools/list`.

Если контекст валиден, но пользователю не доступен ни один tool, корректным
результатом является пустой список, а не ошибка аутентификации:

```json
{
  "tools": []
}
```

## Вызов динамического tool

### 1. Вызов через KitAI Core

После выбора инструмента Agent Runtime инициирует `tools/call`. KitAI Core снова
передаёт JWT и `AgentInfo` в SCSE MCP.

Security-контекст необходимо проверять при каждом запросе. Наличие MCP-сессии
само по себе не означает, что пользователь аутентифицирован на весь срок жизни
сессии.

### 2. Повторная проверка доступа

SCSE MCP повторно получает `McpCallerContext` и проверяет доступ уже к конкретно
вызванному tool. Нельзя полагаться только на ранее возвращённый `tools/list`,
потому что:

- права пользователя могли измениться;
- tool мог быть отключён;
- клиент может вручную вызвать tool, которого не было в его списке;
- ранее полученный список мог быть закеширован.

### 3. Подготовка обращения к backend

Если вызов разрешён, SCSE MCP запрашивает у `mcp-security-starter` данные для
авторизованного обращения к `scse-mid`.

В `scse-mid` передаётся только СУДИР JWT:

```http
Authorization: Bearer <СУДИР JWT>
```

AI HUB JWT и Surface JWT автоматически в backend не передаются, поскольку они
предназначены для другого получателя и другого security-контракта.

### 4. Выполнение в scse-mid

SCSE MCP вызывает REST endpoint `scse-mid`, соответствующий выбранному шаблону.
Backend повторно валидирует СУДИР JWT и проверяет собственные права доступа.

Результатом может быть:

- `resultId` для асинхронно выполняемого запроса;
- готовый результат;
- backend-ошибка, включая отказ в доступе.

Полученный результат SCSE MCP преобразует в MCP tool result и возвращает через
KitAI Core агенту.

## Ошибки и отказы в доступе

Следует различать аутентификацию и авторизацию:

| Ситуация | Предлагаемая реакция |
|---|---|
| Нет обязательного JWT | `401 Unauthorized` |
| JWT невалиден или истёк | `401 Unauthorized` |
| Контекст валиден, но доступных tools нет | Успешный `tools/list` с пустым массивом |
| Контекст валиден, но конкретный tool запрещён | MCP tool error с сообщением об отсутствии доступа |
| `scse-mid` отклонил запрос | Преобразовать backend-ошибку в безопасный MCP tool error |

Нужно отдельно согласовать единый формат ошибок между KitAI Core и SCSE MCP.

## Границы ответственности

### KitAI Core

- передаёт MCP-запрос;
- передаёт согласованный набор JWT и `AgentInfo`;
- не решает, какие SCSE tools доступны пользователю.

### mcp-security-starter

- скрывает техническую работу с JWT;
- возвращает проверенный контекст;
- обеспечивает подготовку токена для downstream-вызова;
- не содержит бизнес-правил доступа к SCSE-шаблонам.

### SCSE MCP

- владеет правилами доступности MCP-tools;
- фильтрует `tools/list`;
- повторно проверяет `tools/call`;
- сопоставляет tool с шаблоном;
- вызывает `scse-mid`.

### scse-mid

- предоставляет API шаблонов и выполнения запросов;
- повторно проверяет СУДИР JWT;
- применяет backend-ограничения доступа;
- остаётся источником бизнес-данных и результатов запросов.

## Вопросы, требующие согласования

Перед реализацией необходимо определить:

1. В каких HTTP-заголовках передаётся каждый JWT.
2. Обязателен ли Surface JWT.
3. Что именно подтверждает AI HUB JWT и когда он может отсутствовать.
4. Формат `AgentInfo` и способ защиты `agentId` от подмены.
5. Как связываются идентичности пользователя, агента и поверхности.
6. Issuer, audience, JWKS и обязательные claims каждого JWT.
7. Где хранятся правила `user × agent × surface × tool`.
8. Как обновляются правила и персональный список tools.
9. Допустимо ли кеширование `tools/list` и каким должен быть ключ кеша.
10. Какой формат ошибок ожидает KitAI Core.
11. Как токены исключаются из логов, трассировок и сообщений модели.

## Краткий текст для объяснения схемы

> Пользователь работает с SCSE не напрямую, а через ИИ-агента. Агент обращается
> к KitAI Core, который выступает MCP-клиентом для нашего SCSE MCP-сервера.
> Вместе с каждым MCP-запросом KitAI Core передаёт security-контекст: опциональный
> токен AI HUB, обязательный пользовательский токен СУДИР, токен поверхности и
> информацию об агенте. Точные заголовки и формат последних двух элементов ещё
> должны быть согласованы.
>
> SCSE MCP не разбирает JWT самостоятельно. Он передаёт входной security-контекст
> в общую библиотеку `mcp-security-starter`. Библиотека рассматривается как
> чёрный ящик и возвращает нормализованный `McpCallerContext` с проверенными
> идентичностями пользователя, агента, поверхности и вызывающей системы.
>
> При запросе `tools/list` MCP использует этот контекст, чтобы вернуть только те
> динамические tools, которые разрешены конкретному пользователю, конкретному
> агенту и конкретной поверхности. При `tools/call` эта проверка выполняется
> повторно, потому что клиент может вызвать инструмент вручную, а права могли
> измениться после получения списка.
>
> Если вызов разрешён, библиотека подготавливает для MCP заголовок Authorization
> с СУДИР JWT. С этим токеном MCP обращается по REST в backend-сервис `scse-mid`.
> Другие токены в backend не передаются. `scse-mid` повторно проверяет СУДИР JWT
> и собственные права, выполняет шаблон и возвращает результат. MCP преобразует
> его в MCP tool result и через KitAI Core возвращает агенту.
>
> Таким образом, библиотека скрывает техническую работу с токенами, SCSE MCP
> принимает прикладное решение о доступности tools, а `scse-mid` остаётся
> защищённым backend-сервисом, который выполняет запросы и повторно контролирует
> доступ.
